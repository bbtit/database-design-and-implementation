# 第3章 Disk and File Management（ディスクとファイルの管理）

前半（3.1〜3.4）はハードウェアとOSの話。後半（3.5）で、SimpleDB のいちばん下の層である **File Manager** を実装する。

## 3.1 永続ストレージ

### HDD の構造とアクセス時間

- ディスクは回転するプラッタでできていて、プラッタには同心円状のトラックがあり、トラックはセクタ（512B 程度）に分かれている。
- ヘッドはすべて1つのアクチュエータにつながっていて、一緒に動く。
- 1回のアクセスにかかる時間は次の3つの合計。
  1. **シーク時間**：ヘッドを目的のトラックまで移動させる時間
  2. **回転待ち**：目的のバイトがヘッドの下に来るまで待つ時間
  3. **転送時間**：実際にバイトを読み書きする時間
- 機械的に動くので、とにかく遅い。

### 速くする工夫

- ディスクキャッシュ：トラック1本分をまとめて先読みする
- シリンダ：同じトラック番号のブロックどうしなら、シークなしでアクセスできる
- ストライピング：複数のディスクに分散して並列に読み書きする

### 信頼性を上げる工夫（RAID）

- RAID-0：ストライピングのみ。1台壊れるとデータ全体が失われる
- RAID-1：ミラーリング
- RAID-4：パリティ専用のディスクを1台持ち、壊れた1台分をXORで復元する

コントローラが複数のディスクを「1台の仮想ディスク」に見せている。

### フラッシュ（SSD）

完全に電子的に動くのでHDDより速いが、RAMよりは遅い。そのためOSはディスクと同じ扱いをする。

## 3.2 ブロックレベルのインタフェース

- OSはセクタを隠して、固定サイズの**ブロック**単位でアクセスさせる。
- ブロックの中身を直接いじることはできない。**ページ**（ブロックと同じサイズのメモリ領域）に読み込み、ページを変更してから書き戻す。
- 空きブロックの管理方法は2つある。
  - **ディスクマップ**：ブロックごとに1ビット。どこが空いているか全体を把握しやすい
  - **フリーリスト**：空きチャンクを連結リストでつなぐ。追加で必要な領域が少ない

## 3.3 ファイルレベルのインタフェース

- ファイルは「名前の付いたバイト列」で、任意の位置から任意の長さを読み書きできる。
- OS側でのファイルの実装方式は3つある。
  - 連続割り当て
  - エクステント方式（連続したブロックの塊を並べる）
  - インデックス方式（UNIX の inode のように、ブロックの一覧を別に持つ）

## 3.4 DBとOSの関係（設計上の判断）

| 方式 | 利点 | 欠点 |
|---|---|---|
| raw ディスクをブロックレベルで直接扱う | ブロックの配置を完全に制御できる | 実装も運用も難しい |
| ファイルを普通のファイルとして扱う | 実装が簡単 | ブロック境界が分からず、ページ管理をOSに任せることになる（DBのクエリには不向き） |
| **折衷案：OSのファイルを「raw ディスク」のようにブロック単位で使う** | **SimpleDB、Oracle、Derby はこれ** | seek のときにOSが余分なアクセスをすることがあるが、無視できる程度 |

## 3.5 SimpleDB の File Manager

DBはディレクトリ1つに置かれ、テーブル・インデックス・ログ・カタログがそれぞれ別のファイルになる。クラスは3つ。

### `BlockId`

（ファイル名, ブロック番号）の組。等価比較とハッシュができる必要がある（後の章でマップのキーに使う）。

### `Page`

ブロック1個分のバイト列。

- 扱う型は int・blob（`[長さ int][バイト列]`）・string（blob として保存）
- どのオフセットに何を置いたかはクライアント側が覚えておく
- `maxLength(n)` = 4 + n × 1文字あたりの最大バイト数。ASCII なら 4 + n
- コンストラクタは2つ。ブロックサイズを指定するもの（バッファ管理用）と、既存の `[]byte` をラップするもの（ログ管理用）

### `FileMgr`

- `read` / `write`：`blk.number * blocksize` の位置まで seek して、ブロック1個分をまとめて読み書きする。**1回の呼び出しでディスクアクセスはちょうど1回**になる
- `append`：ファイルの末尾に空のブロックを書き足してファイルを伸ばす
- `length`：ファイルサイズ ÷ ブロックサイズ
- ファイルは **`"rws"` モード**（書き込みのたびに即座にディスクへ同期する）で開く。「いつ書かれたか」を正確に知る必要があるため。第5章のリカバリで重要になる
- read / write / append は **synchronized**。seek と read の間に別スレッドが割り込むと、違うブロックを読んでしまうため
- 開いたファイルはマップにキャッシュする。起動時に `temp` で始まるファイル（第13章の一時テーブル）を削除する
- デフォルトのブロックサイズは 400B。わざと小さくして、ブロックがたくさんできるようにしている

## Go で実装するときのポイント

- `Page`：`[]byte` と `encoding/binary.BigEndian` の `PutUint32` / `Uint32` で素直に書ける。Java の ByteBuffer はビッグエンディアンなので、それに合わせておくとよい。
- `BlockId`：比較可能な値型の struct（`struct{ Filename string; Blknum int }`）にすれば、そのまま `map` のキーに使える。`hashCode` は不要。
- `"rws"` に相当するのは `os.OpenFile(path, os.O_RDWR|os.O_CREATE|os.O_SYNC, 0644)`。
- seek + read の競合は `f.ReadAt` / `f.WriteAt`（`pread` / `pwrite`）を使えば原理的に起きない。ただし `openFiles` マップへのアクセスや append の一貫性のために `sync.Mutex` は必要。
- 文字列は ASCII 前提なら `maxLength = 4 + n`。UTF-8 を許すなら `4 + n*utf8.UTFMax`。

## 復習：つまずいたポイント

第3章を実装しながら質問して、理解があやしかった点のまとめ。コード中の名前は自分の実装（`BlockID`・`Blknum()` など）に合わせている。

### 用語と概念

#### セクタ・ブロック・ページ・raw ディスクの違い

| 用語 | 誰が決める単位か | 置き場所 | 大きさ |
|---|---|---|---|
| セクタ | ハードウェア | ディスク | 512B 程度 |
| ブロック | OS（SimpleDB では FileMgr） | ディスク上の枠 | 4KB 程度（SimpleDB のデフォルトは 400B） |
| ページ | DB | メモリ上の、ブロックの写し | ブロックと同じ大きさ |

- ブロックの中身はディスク上では直接いじれない。ページに読み込み、書き換えて、書き戻す。
- raw ディスクは、ファイルシステムを載せていないディスク。DB がブロックの配置を全部自分で管理する。
- SimpleDB は折衷案を取っている。普通の OS ファイルを作り、それを raw ディスクのつもりでブロック単位に扱う。

#### ブロックサイズ・ブロック番号・ブロック数を混同しない

| 言葉 | 意味 | テストでの値 |
|---|---|---|
| ブロックサイズ | ブロック **1個の大きさ** | 400 |
| ブロック番号 | **何番目の**ブロックか（**0 始まり**） | 2 |
| ブロック数 | ファイルに **いくつ** あるか（`Length()`） | 3 |

- ブロック 2 に書くと、手前の 0 と 1 も存在することになる。間は OS が 0 で埋めてファイルを伸ばすので、ファイルサイズは 1200 バイト、ブロック数は `1200 ÷ 400 = 3`。
- `Append` は「今のブロック数」を新しいブロック番号として使う。配列の `len(a)` と、次に append される `a[len(a)]` の関係と同じ。

#### blob とは

- Binary Large OBject の略。本の Page では「中身を解釈しない、任意の長さのバイト列」くらいの意味。
- 可変長なので `[長さ 4 バイト][中身]` の形で保存する。string はこの blob の上に乗った変換機能にすぎない。
- 第4章のログレコードは、ログマネージャから見ると中身の分からない blob として運ばれる。

### 本の読み方

#### Fig 3.11 はインタフェース定義ではなく API 一覧

- 並んでいるのは、具体的なクラスの公開メソッドのシグネチャ（名前・引数・戻り値）。実装は Fig 3.13〜3.15 にある。
- Java でクラス名と同じ名前のもの（`BlockId(...)` など）はコンストラクタ。Go では `NewXxx` 関数にする。

#### Go の interface はまだ要らない

- 本の3つの型は、どれも実装が1つしかない具体クラス。
- Go では、interface は実装が複数になったときや、テストで差し替えたくなったときに、**使う側**が定義する。
- 本当に interface が必要になるのは、第8章の `Scan`、第10章の `Plan` あたりから。

#### 一時テーブルの削除処理（第13章用）は今は不要

- 本の FileMgr にある「起動時に `temp` で始まるファイルを削除する」処理は、第13章の一時テーブル（`TempTable` が作る `tempN`）の後始末。
- 第13章の本文は、この処理が FileMgr にすでにある前提で一言触れるだけで、「ここを編集せよ」とは書いていない。**第13章に入ったら自分で思い出して入れ直す。**
- 入れ直すときは、`temperature` のようなテーブル名まで消さないように、一時ファイル用のディレクトリを分けるなどの工夫をする。

### Page の中身

#### offset はだれが管理するのか

- Page は何も覚えていない。「どこに何を置くか」というレイアウトは上の層が決める。
  - **計算で決める**：スキーマから求める。第6章のレコードは `i * slotSize + フィールドの offset`。
  - **ページに書いておく**：先頭などの決まった位置に、次の位置を書いておく。第4章のログの boundary、第12章の B-tree のヘッダ。
- 間違った offset で get すると、でたらめな値が返る。

#### blob の offset は長さ情報の先頭を指す

- `SetBytes(88, b)` の 88 は「長さ」の位置。中身は `88 + 4 = 92` から始まる。+4 するのは Page の中の仕事。
- ただし、**次の値を置く位置の計算は呼び出し側の仕事**。`88 + MaxLength(13) = 88 + 17 = 105`。中身の長さだけ足して `88 + 13` にすると、値が重なって壊れる。

#### GetInt の中身：バイト・ビッグエンディアン・uint と int

```go
int(int32(binary.BigEndian.Uint32(p.buf[offset:])))
```

1. `p.buf[offset:]`：offset から先のバイト列
2. `BigEndian.Uint32`：先頭4バイトを「上位バイトが先」として、符号なし32ビット整数に組み立てる。345 は `00 00 01 59`。
3. `int32(...)`：符号ありとして解釈し直す。`FF FF FF FF` は uint32 だと 4294967295、int32 だと -1。
4. `int(...)`：Go の int（64ビット）にする。

- ビッグエンディアンにしているのは、Java の ByteBuffer に合わせたから。読みと書きで同じ流儀を使っていればどちらでもよい。

#### GetBytes はコピーを返す

- `p.buf[start:end]` をそのまま返すと、Page のメモリを共有したままになる。後で Page が書き換わる（第4章でバッファが入れ替わる）と、受け取った値まで変わってしまう。
- `make` した新しいスライスに `copy` して返す。

#### `NewPage(16)` はテスト用の大きさ

- `NewPage` の引数は「何バイト確保するか」だけ。Page 自身はブロックサイズを知らない。
- Page 単体のテストなら、使う分（int なら4バイト）以上あれば何でもよい。
- FileMgr の Read/Write に渡すときだけは、`NewPage(fm.BlockSize())` でブロックと大きさを揃える。

### FileMgr の中身

#### なぜ FileMgr がブロックサイズを知っているのか

- OS のファイルはただのバイト列で、ブロックを知らない。「ファイル＝ブロックの並び」として見せる翻訳係が FileMgr。
- ブロック番号からバイト位置への換算 `Blknum() × blocksize` をここに閉じ込めておけば、上の層はバイト位置を一切計算しなくて済む。
- `int64(...)` にするのは、`ReadAt` / `WriteAt` の offset が int64 だから。**掛ける前に**両方を int64 にして、2GB を超えてもあふれないようにする。

#### `length` と `Length` がある理由

- `Length`（公開）はロックを取る。`length`（内部）はロックを取らない。
- `Append` はロックを持ったまま「数える → 書く」を行う。中で `Length` を呼ぶと、同じ goroutine が2回 Lock することになる。
- **Go の `sync.Mutex` は再入できない**ので、これはデッドロックになる（Java の synchronized は再入できるので、Java 版には分割がない）。
- 「公開メソッドがロックを取り、内部メソッドはロック済み前提で動く」のは Go の定番パターン。

#### `os.OpenFile` のフラグとパーミッション

- `O_RDWR|O_CREATE|O_SYNC` は、読み書き両方で開く／なければ作る／書き込みはディスクに届いてから戻る、の組み合わせ。Java の `"rws"` に相当する。
- フラグはビットの OR（`|`）で組み合わせる。
- `0o644` は8進数のパーミッション（所有者 rw、他は r）。ファイルを新しく作るときだけ使われる。
- 親ディレクトリは作ってくれないので、`NewFileMgr` で先に `MkdirAll` しておく。

### Go の文法・書き方

#### レシーバ付きメソッドの読み方

```go
func (p *Page) GetInt(offset int) int
//   レシーバ   名前     引数        戻り値
```

- `(p *Page)` は、このメソッドを `*Page` に紐づけるという宣言で、Java の `this` に名前を付けたようなもの。
- 大文字で始まる名前は公開（Java の public）、小文字は同じパッケージ内だけ。

#### 値で返すかポインタで返すか

| | 値（`BlockID`） | ポインタ（`*Page`, `*FileMgr`） |
|---|---|---|
| 作ったあと変わるか | 変わらない | 書き換える |
| 何で同じとみなすか | 中身が同じなら同じ（`==`、map のキーに使える） | 同じ実体かどうか |

- `BlockID` をポインタにすると、`==` がアドレスの比較になり、map のキーとしても使えなくなる。
- `sync.Mutex` を含む struct（FileMgr）はコピーしてはいけないので、必ずポインタで持つ。

#### `:=` と `=`

- `:=` は「宣言＋代入」なので、左辺に **新しい変数が1つ以上** 必要。`_` は数えない。
- すでに宣言済みの `err` に入れ直すだけなら `=` を使う。または `if _, err := ...; err != nil {}` の形にして、スコープを if の中に閉じる。

#### エラー処理の落とし穴

- `fmt.Errorf(...)` は作るだけで、**`return` しないと何も起きない**。getFile の失敗を返し忘れると、nil の `f` を使って panic する。
- `return BlockID{}, nil` のようにエラーを nil で返すと、失敗が握りつぶされて、空の BlockID が「成功」として上に渡る。
- 存在確認は `errors.Is(err, os.ErrNotExist)`。`os.IsNotExist(err)` は古い書き方。
  - `os.Stat(path)` がエラーなしなら、ファイルはある。
  - `!errors.Is(err, os.ErrNotExist)` なら「消えていない」（または別のエラー）。

#### 名前の揺れはビルドエラーになる

- お手本（`BlockId` / `Number()` / `contents()`）と、自分の命名（`BlockID` / `Blknum()`）が混ざってビルドが通らなかった。**どちらかに決めて全ファイルで揃える。**
- Go では略語を全部大文字にする慣習がある（`ID`、`URL`）。`BlockID` のほうが正しく、`BlockId` は staticcheck に怒られる。
- `newBlockID` は小文字なので、ほかのパッケージからは呼べない。第4章で buffer / log パッケージから使うので、`NewBlockID` にしておく必要がある。

#### パッケージコメント

- 「at least one file in a package should have a package comment」は、`// Package file ...` で始まるコメントを `package file` の直前に書けば消える。
- パッケージ内の1ファイル（慣習では `doc.go`）に書けば十分。

#### エディタの診断と実際のビルド結果は別物

- `expected ';', found 'ILLEGAL'` は、全角スペースなど Go の文法で使えない文字があるときに出る。
- 保存済みのファイルには問題がなくても、エディタ（gopls）が古い診断を表示し続けることがある。**迷ったらターミナルで `go build ./...` を実行して確かめる**。エディタのほうは、言語サーバーを再起動すれば直る。
